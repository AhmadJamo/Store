## 1. القرار التنفيذي / Executive decision

هذا المشروع قائم ويحتوي على وظائف صحيحة لا يجوز استبدالها بصورة شاملة. المسار الحالي المسمى `Sale` (بيع) هو عملياً **فاتورة بيع فورية مع دفع وخروج مخزون مباشر**، ويخدم البيع بالجملة و`POS` (نقطة البيع). لا يمثل عرض سعر أو طلب بيع أو تسليماً أو فاتورة آجلة مستقلة.

لذلك يكون التطوير **إضافياً ومتدرجاً**:

1. الحفاظ على `Sale` (البيع الفوري الحالي) وبياناته التاريخية.
2. عدم إعادة تسمية سجلاته القديمة أو تحويلها آلياً إلى طلبات وتسليمات وفواتير مخترعة.
3. إنشاء دورة جديدة منفصلة: عرض سعر ← طلب بيع ← حجز ← تسليم ← فاتورة زبون ← تحصيل.
4. إعادة استخدام سلطات المخزون والمحاسبة والترقيم والصلاحيات وعزل الشركات الحالية.
5. إيقاف إنشاء البيع بالجملة القديم لاحقاً فقط بعد نجاح رحلة المبيعات الجديدة وثبوت التقارير والتوافق، مع إمكان إبقاء `POS` (نقطة البيع) كمسار بيع نقدي سريع مضبوط.

هذه الوثيقة لا تنفذ إعادة البناء، ولا تغيّر قاعدة البيانات أو سلوك التشغيل. اكتملت البوابة التوثيقية `SAL-005`، والخطوة التشغيلية التالية هي `SAL-010`.

## 2. نطاق التدقيق / Audit scope

تمت مراجعة خريطة الحل والطبقات والوثائق والكود ذي العلاقة، بما يشمل:

- `Domain` (طبقة المجال): المنتجات، الزبائن، البيع، المرتجعات، المخزون، الحجز، المحاسبة، الإعدادات والأمان.
- `Application` (طبقة التطبيق): خدمات البيع والترحيل والمرتجعات والخصم والحجز والعملات والترقيم.
- `Infrastructure` (طبقة البنية التحتية): `DbContext` (سياق قاعدة البيانات)، المستودعات، خرائط `EF Core` (إطار ربط الكائنات بقاعدة البيانات)، العزل والتدقيق و`UnitOfWork` (وحدة العمل).
- `Web` (طبقة العرض): المتحكمات، صفحات `Razor` (واجهات الخادم)، التنقل، الترجمة والصلاحيات.
- الترحيلات الحالية واختبارات `SecurityRegression` (اختبارات الانحدار الأمني) و`InventorySqlIntegration` (اختبارات تكامل المخزون مع قاعدة البيانات).
- وثائق المبيعات والمخزون والمحاسبة والصلاحيات والخارطة الرئيسية وقرارات التصميم السابقة.

| مرتجع البيع | مرتجع جزئي/كامل، سقف تراكمي، تتبع، إعادة مخزون، عكس إيراد وضريبة وكلفة | صحيح للمبيعات الفورية المرحلة |
| الترقيم | تسلسل مركزي آمن ومتزامن للبيع بالجملة و`POS` والمرتجع والقيد | قابل للتوسعة لأنواع المستندات الجديدة |

| العملات | عملة شركة وأسعار صرف مؤرخة مستخدمة في دورة المشتريات | يعاد استخدامها؛ المبيعات الحالية غير متعددة العملات |
| الواجهة | صفحات قائمة/إنشاء/تفاصيل للبيع وواجهة `POS` ومرتجعات | تبقى للمسار المتوافق أثناء التطوير |

### 3.2 ما يجب أن يبقى دون تغيير جوهري / Preserve unchanged

- اتجاه الاعتماد: `Web → Application → Domain` (العرض ثم التطبيق ثم المجال).
- `UnitOfWork` (وحدة العمل) الحالية ومعاملاتها من مستوى `Serializable` (قابل للتسلسل) للعمليات الحساسة.
- `ProductStock` (رصيد المنتج في المستودع) كسلطة الكمية والقيمة أثناء فترة الانتقال.
- `InventoryBalance` (رصيد المخزون التفصيلي) كإسقاط للتوفر والحجوزات.
- `StockTransaction` (حركة تكلفة المخزون) و`StockMovement` (الحركة الفعلية) مع تطوير الأنواع المطلوبة للتسليم.
- `InventoryTrackingService` (خدمة تتبع المخزون) وسياسات السحب والتتبع باللوط أو الرقم التسلسلي.
- `JournalPostingService` (بوابة ترحيل القيود) والفترات المالية ومنع تكرار المصدر.
- `DocumentSequence` (تسلسل أرقام المستندات) والصلاحيات الحالية وعزل الشركات.
- تصنيف المنتج والوصفات ومتوسط التكلفة المتحرك وتكلفة البيع التاريخية.
- البيع الفوري و`POS` (نقطة البيع) والمرتجعات القديمة كسجلات متوافقة لا تُعاد كتابتها.

### 3.3 تصنيف المسار القديم / Legacy compatibility classification

| السلوك الحالي | التصنيف المستقبلي |
|---|---|
| إنشاء `Sale` وخروج المخزون فوراً | `Legacy Immediate Sale` (بيع فوري قديم) |
| رقم `WholesaleSale` | رقم فاتورة البيع الفوري القديم، وليس رقم طلب بيع |
| دفع إلزامي أثناء الإنشاء | تسوية فورية، وليس تخصيص دفعة على ذمة |
| زر الترحيل المحاسبي اللاحق | ترحيل فاتورة البيع الفوري الحالية |
| `SalesReturn` الحالي | مرتجع بيع فوري مرتبط بالفاتورة القديمة |

يمنع تفسير أي سجل قديم على أنه عرض سعر أو طلب بيع أو تسليم مستقل لعدم وجود دليل تاريخي على تلك المراحل.

## 4. نقاط القوة القابلة لإعادة الاستخدام / Reusable foundations

1. **الكتالوج:** يدعم الاسم والكود والباركود والقالب والمتغير والتصنيف والوحدات والتتبع.
2. **المخزون:** يملك التوفر والحجز والمواقع والتتبع والحركات ومتوسط التكلفة والتزامن.
3. **المحاسبة:** الترحيل المركزي، منع المصدر المكرر، الفترات، أرقام القيود والحسابات المربوطة.
4. **المشتريات:** يقدم نمطاً مثبتاً لفصل الطلب والاستلام والفاتورة والدفع والحالات متعددة الأبعاد.
5. **الأمان:** الصلاحيات على الخادم، عزل المستأجر، العلاقات المركبة ومنع الكتابة عبر الشركات.
6. **الترقيم:** إضافة أنواع جديدة أفضل من إنشاء عدادات مستقلة.
7. **العملات:** سياسة سعر صرف مؤرخ وقيم أصلية وقيم بعملة الشركة مطبقة في المشتريات ويمكن تعميمها بعقد مشترك.
8. **إرشاد المستخدم:** رسائل الخطأ القابلة للتنفيذ والخطوة التالية بعد كل عملية يمكن تمديدها للمبيعات.
9. **الترجمة:** مورد مشترك للإنجليزية والعربية ودعم `RTL` (اتجاه من اليمين إلى اليسار).

## 5. الفجوات والتعارضات / Gaps and conflicts

### 5.1 فجوات حرجة / Critical gaps

| الفجوة | الدليل الحالي | الأثر |
|---|---|---|
| البيع والتسليم والفاتورة والدفع كعملية واحدة | `SaleService.CreateAsync` ينقص المخزون ويتطلب وسيلة دفع | يمنع الآجل والتسليم والفوترة الجزئية |
| لا يوجد عرض سعر أو طلب بيع | لا كيانات أو جداول أو خدمات لهذه المستندات | لا توجد دورة مبيعات احترافية |
| التأكيد يساوي خروج المخزون في المسار الحالي | إنشاء البيع يستدعي إزالة المخزون مباشرة | يتعارض مع فصل الحجز عن التسليم |
| لا يوجد مستند تسليم | لا `Delivery` (تسليم) أو خطوط تسليم | لا يمكن التسليم الجزئي أو المرتجع من تسليم محدد |
| لا توجد فاتورة زبون مستقلة | `Sale` يحمل رقم فاتورة وسلوك البيع والدفع | لا يمكن فواتير متعددة أو دفعات مقدمة |
| لا يوجد تحصيل وتخصيص | وسيلة الدفع مطلوبة ولا يوجد `CustomerPaymentAllocation` (تخصيص دفعة زبون) | لا يدعم سداداً جزئياً أو دفعة لعدة فواتير |
| حساب الزبون غير مستخدم في ترحيل البيع | الترحيل يدين حساب وسيلة الدفع مباشرة | لا توجد ذمم مدينة فعلية |
| لا حالات مستقلة | لا حالة طلب/تسليم/فوترة/دفع | لا يمكن تمثيل تقدم المستندات بدقة |
| لا تثبيت كامل لبيانات السطر | تفاصيل البيع تقرأ اسم المنتج الحالي؛ لا كود/اسم/وحدة مثبتة | تغيير المنتج يغيّر عرض الوثيقة التاريخية |
| لا وحدة بيع مثبتة | كمية `SaleItem` بلا `MeasurementUnitId` أو معامل تحويل | لا يدعم قطعة/حزمة/كرتونة بصورة صحيحة |
| تسعير غير قابل للتفسير | السعر يختار مباشرة من حقلي المنتج | لا قوائم أسعار أو قواعد كمية/زبون/عملة |
| ضريبة رأس واحدة | `Sale.ApplyTax` يثبت ضريبة واحدة على كامل المستند | لا ضرائب مختلطة أو فئة ضريبية للمنتج |
| لا مفتاح منع تكرار لإنشاء البيع | منع التكرار موجود في القيد فقط | إعادة إرسال الطلب قد تنقص المخزون مرتين |
| سجل تدقيق غير دلالي | التدقيق العام يحفظ أضيف/عُدّل/حُذف فقط | لا سبب ولا انتقال حالة ولا قيمة قبل/بعد |

### 5.2 ديون تقنية تحتاج معالجة في سياق المرحلة / Contextual technical debt

- `SalesController` (متحكم المبيعات) يجلب المنتجات والمستودعات والأرصدة والزبائن والدفع والضريبة من المستودعات مباشرة؛ يجب نقل تجهيز صفحة المبيعات الجديدة إلى خدمة تطبيق.
- `SaleService` (خدمة البيع) تجمع التسعير والخصم والوصفة والتتبع والمواقع والكلفة والترقيم والتحقق من `POS` (نقطة البيع) في خدمة واحدة كبيرة.
- منطق الخصم موجود في `Sale` و`SaleItem` و`DiscountCalculator` (حاسبة الخصم)، ما يعرّضه للاختلاف.
- حساب الضريبة موزع بين `Sale` والترحيل والمرتجع، ويجب توحيده قبل الفواتير الجديدة.
- صلاحية `Sales.Create` تحمي الإنشاء والترحيل معاً؛ فصل المهام يحتاج صلاحيات مستقلة.
- صلاحيات `Sales.Edit/Delete` معرفة من دون أفعال مطابقة؛ لا تُستخدم كأساس للمستندات الجديدة دون تعريف واضح.
- واجهة تفاصيل البيع تعرض اسم المنتج الحالي بدلاً من وصف تاريخي مثبت.
- لا يوجد `RowVersion` (رمز إصدار الصف) على `Sale`، ولا حالة تمنع تعديل المعنى التشغيلي بعد الإنشاء؛ الحماية الحالية تعتمد على تنفيذ العملية في معاملة واحدة.

### 5.3 مفاهيم مفقودة / Missing concepts

- ملف زبون احترافي، جهات اتصال، عناوين فوترة وشحن، شروط دفع، عملة، حد ائتماني وحالة نشاط.
- موظف مبيعات وفريق مبيعات وتعيينهما إلى الطلب.
- قائمة أسعار وقاعدة سعر ونتيجة سعر قابلة للتفسير.
- عرض سعر وقالب عرض ومنتجات اختيارية.
- طلب بيع بحالات وتاريخ مستقل.
- طلب مخزون مرتبط بطلب البيع وتنفيذ حجز جزئي/كامل.
- مستند تسليم، تجهيز، تسليم جزئي وكمية متبقية.
- فاتورة زبون، سطر مصدر، دفعة مقدمة، إشعار دائن وحالة ذمة.
- دفعة زبون وتخصيصاتها وربطها بحساب القبض.
- سياسة ائتمان وتحذيرات وموافقات مبيعات.
- تحليل هامش من لقطات السعر والكلفة التاريخية.

## 6. الحدود المنطقية المقترحة / Recommended bounded contexts

لا تنشأ مشاريع مستقلة جديدة الآن. تبقى الحدود مجلدات منطقية داخل الطبقات الحالية:

| السياق | الملكية المقترحة |
|---|---|
| `Foundation` (الأساس) | الشركة، الفرع، العملات، الوحدات، الترقيم، الزمن والمستخدم الحالي |
| `Catalog` (الكتالوج) | المنتج والقالب والمتغير والتصنيف وخصائص البيع/المخزون |
| `Customers` (الزبائن) | ملف الزبون، جهات الاتصال، العناوين وشروطه التجارية |
| `Pricing` (التسعير) | قوائم الأسعار والقواعد وحل السعر ومصدره |
| `Sales` (المبيعات) | عروض الأسعار وطلبات البيع والحالات والتاريخ |
| `Inventory` (المخزون) | التوفر والحجز والتجهيز والتسليم والحركات والتتبع |
| `Invoicing` (الفوترة) | فواتير الزبائن، الإشعارات الدائنة ومصادر السطور |
| `Accounting` (المحاسبة) | القيود والذمم والفترات وخرائط الحسابات |
| `Payments` (التحصيل) | دفعات الزبائن والتخصيص والتسوية والاسترداد |
| `Reporting` (التقارير) | إسقاطات القراءة ومؤشرات المبيعات والهامش |
| `Notifications` (الإشعارات) | الإشعارات المستقبلية الناتجة من حقائق الأعمال |

## 7. خريطة الاعتماد / Dependency map

```text
Tenancy + Identity + Foundation
             │
     ┌───────┼────────┐
     ▼       ▼        ▼
  Catalog  Customers  Pricing + Tax
     └───────┼────────┘
             ▼
       Quotation / Sales Order
             │
      ┌──────┴───────────┐
      ▼                  ▼
Inventory Demand     Invoicing Eligibility
      │                  │
Reservation              ▼
      │             Customer Invoice
      ▼                  │
Delivery ────────────────┤
      │                  ▼
Stock Movement       Accounting / AR
      │                  │
      └──────┐           ▼
             ▼      Customer Payments
        Cost Evidence         │
             └──────┬─────────┘
                    ▼
            Returns / Credit / Refund
```

القواعد الأساسية:

- `Sales` (المبيعات) لا تكتب أرصدة المخزون أو جداول القيود مباشرة.
- `Inventory` (المخزون) لا يقرر السعر أو الضريبة أو الذمة.
- `Invoicing` (الفوترة) لا تعتبر التسليم دفعاً.
- `Payments` (التحصيل) يخصص على الفواتير ولا يغيّر قيمة الفاتورة الأصلية.
- `Accounting` (المحاسبة) تستقبل طلب ترحيل محسوباً عبر البوابة المركزية.

## 8. حدود التجمعات / Aggregate boundaries

### 8.1 `Customer` (الزبون)

يمتلك الملف التجاري الأساسي والحالة وشروط الدفع والعملة والائتمان. جهات الاتصال والعناوين أطفال مضبوطون. رصيد الذمة **مشتق** من الفواتير والدفعات ولا يخزن كرقم حر قابل للتعديل.

### 8.2 `PriceList` (قائمة الأسعار)

يمتلك العملة والقناة وفترة الصلاحية وقواعد السعر المرتبة. حل السعر خدمة مجال/تطبيق حتمية تعيد السعر ومصدر القاعدة وتاريخها، ولا تعدّل المنتج.

### 8.3 `SalesQuotation` (عرض السعر)

يمتلك رقم العرض والزبون والعناوين المثبتة والعملة والصلاحية والبائع والفريق والشروط والسطور والاختيارات والحالة والتاريخ. قبوله ينشئ طلب بيع مرة واحدة.

### 8.4 `SalesOrder` (طلب البيع)

يمتلك الالتزام التجاري المثبت والكمية المطلوبة والحالات التجارية وسجل القرارات. لا يملك الرصيد الفعلي ولا القيد ولا الدفعة. تقدم التسليم والفوترة والدفع إسقاط مشتق من المستندات التابعة.

### 8.5 `InventoryReservation` (حجز المخزون)

يبقى تجمعاً مستقلاً في سياق المخزون ويرتبط بمصدر `SaleOrder` (طلب بيع). يملك الكمية المحجوزة والموقع والحالة. لا يصبح حقلاً داخل طلب البيع.

### 8.6 `SalesDelivery` (تسليم المبيعات)

يمتلك خطوط التسليم من طلب واحد، والكميات المجهزة والمسلّمة والمتبقية والتتبع والحالة والتاريخ. ترحيله هو سلطة خروج المخزون وتثبيت كلفة التسليم.

### 8.7 `CustomerInvoice` (فاتورة الزبون)

يمتلك هوية الفاتورة ومصادر السطور والعملة وسعر الصرف والضريبة والإجماليات والحالة. سطر الفاتورة يثبت الوصف والوحدة والسعر والخصم والضريبة والقيم الأصلية وقيم عملة الشركة.

### 8.8 `CustomerPayment` (دفعة الزبون)

يمتلك المبلغ والعملة ووسيلة الدفع والمرجع والتخصيصات. كل تخصيص يربط دفعة بفاتورة ويمنع تجاوز الرصيد المستحق بالتزامن.

### 8.9 الإرجاع والائتمان / Return and credit

على المدى المستهدف تكون الموافقة على الإرجاع واستلام البضاعة وفحصها والتصرف بها منفصلة عن `CustomerCreditNote` (إشعار الزبون الدائن) و`CustomerRefund` (رد المبلغ). يبقى `SalesReturn` الحالي خاصاً بمسار البيع الفوري القديم.

## 9. العقود والحقائق الداخلية / Internal contracts and facts

لا يضاف ناقل رسائل موزع. تبدأ العقود داخل العملية الحالية وبنفس `UnitOfWork` (وحدة العمل) عندما تتطلب الذرية:

| الحقيقة | المنتج | المستهلك المتوقع |
|---|---|---|
| `QuotationAccepted` (قُبل عرض السعر) | المبيعات | إنشاء طلب البيع مرة واحدة |
| `SalesOrderConfirmed` (تأكد طلب البيع) | المبيعات | المخزون ينشئ/يحدّث الحجز |
| `SalesOrderCancelled` (ألغي طلب البيع) | المبيعات | المخزون يحرر الحجز |
| `DeliveryPosted` (رُحّل التسليم) | المخزون | تحديث تقدم الطلب وأهلية الفوترة وتثبيت الكلفة |
| `CustomerInvoicePosted` (رُحّلت فاتورة الزبون) | الفوترة | المحاسبة تنشئ الذمة والإيراد والضريبة |
| `CustomerPaymentPosted` (رُحّلت دفعة الزبون) | التحصيل | المحاسبة تسوي الذمة وتحدّث التخصيصات |
| `SalesReturnReceived` (استُلم مرتجع البيع) | المخزون | إتاحة الإشعار الدائن حسب نتيجة الفحص |
| `CustomerCreditNotePosted` (رُحّل الإشعار الدائن) | الفوترة | المحاسبة تعكس الذمة والإيراد والضريبة |

هذه أسماء حقائق تصميمية وليست أحداثاً مطبقة. لا يستخدم `outbox` (صندوق إرسال موثوق) إلا عندما يظهر مستهلك غير متزامن أو خارجي حقيقي.

## 10. حدود المعاملات ومنع التكرار / Transaction and idempotency boundaries

| الأمر | حدود المعاملة المطلوبة | مفتاح منع التكرار |
|---|---|---|
| قبول عرض السعر | تغيير العرض + إنشاء طلب واحد | عرض السعر + نسخة القبول |
| تأكيد طلب البيع | الحالة + التاريخ + الحجز الكامل/الجزئي | الطلب + أمر التأكيد |
| إعادة تخصيص الحجز | تحرير القديم + حجز الجديد | الطلب + إصدار إعادة التخصيص |
| ترحيل التسليم | استهلاك الحجز + الرصيد + التتبع + حركة الكلفة + الحركة الفعلية + حالة التسليم | رقم التسليم/السطر |
| ترحيل الفاتورة | حالة الفاتورة + القيد + الذمة | نوع المصدر + رقم الفاتورة |
| ترحيل الدفعة | الدفعة + التخصيصات + القيد | مرجع طلب الدفع |
| استلام المرتجع | التتبع + الرصيد + الحركات + التصرف | رقم الاستلام/السطر |
| ترحيل الإشعار الدائن | الإشعار + القيد + تخفيض المستحق | نوع المصدر + رقم الإشعار |

كل أمر مالي أو مخزني غير قابل للتكرار يجب أن يقبل مفتاح طلب ثابتاً أو يعتمد هوية مصدر فريدة في قاعدة البيانات. إعادة الطلب نفسه تعيد النتيجة الأصلية أو تعارضاً آمناً، ولا تنشئ أثراً ثانياً.

- إنشاء الفاتورة لا يمنح ترحيلها.
- تسجيل الدفعة لا يمنح عكسها.
- تجاوز السعر أو الخصم أو الائتمان صلاحيات مستقلة مع سبب مثبت.

## 12. أثر قاعدة البيانات / Database migration implications

### 12.1 استراتيجية آمنة

- ترحيلات إضافية فقط في المراحل الأولى.
- عدم حذف أو تغيير معنى `Sales` و`SaleItems` و`SalesReturns` الحالية.
- عدم نقل السجلات القديمة إلى الجداول الجديدة تلقائياً.
- إضافة `TenantId` (معرف الشركة المستأجرة) والعلاقات المركبة والفلاتر لكل نوع تشغيلي جديد.
- إضافة `RowVersion` (رمز إصدار الصف) للحالات القابلة للتنافس.
- فهارس فريدة حسب الشركة لأرقام المستندات ومفاتيح منع التكرار.
- دقة كمية مقصودة مثل `decimal(24,6)` ودقة مالية مثل `decimal(18,2)` ومعدل صرف مثل `decimal(24,12)` وفق سياسة المشروع.
- علاقات `Restrict` (منع الحذف) للحقائق التاريخية و`Cascade` (حذف تابع) فقط لأطفال مسودة لا يملكون معنى مستقلاً.

## 13. مخاطر كسر الموجود / Compatibility risks

| الخطر | التحكم المقترح |
|---|---|
| تغيير تقارير البيع القديمة | إبقاء جداول `Sale` ومساراتها ووسمها كبيع فوري قديم |
| احتساب الكمية مرتين | طلب البيع يحجز فقط؛ التسليم وحده ينقص `OnHand` (المتوفر فعلياً) |
| فوترتان لنفس الكمية | تخصيص مصدر فريد وسقف تراكمي حسب سطر الطلب/التسليم |
| دفع يتجاوز المستحق | قفل/تزامن على الفاتورة والتخصيص داخل معاملة قابلة للتسلسل |
| اختلاف السعر التاريخي | تثبيت نتيجة السعر ومصدرها والوحدة والعملة على السطر |
| اختلاف اسم المنتج أو العنوان | لقطات محددة تاريخياً على العرض والطلب والفاتورة |
| إفساد متوسط التكلفة | التسليم يستخدم خدمة المخزون ويثبت كلفة الحركة؛ لا يكتب قيمة حرة |
| تعارض `POS` مع الطلبات | إبقاء `POS` مساراً فورياً مستقلاً حتى تقرر سياسة دمجه |
| اختلاف التقارير بين القديم والجديد | عمود/نوع مصدر واضح وإسقاط تقريري يجمعهما صراحة |
| توسعة عامة مبكرة | بناء كل تجريد عند أول استخدام فعلي فقط |

## 14. الاختبارات المطلوبة / Required tests

### 14.1 اختبارات المجال

- انتقالات العرض والطلب والتسليم والفاتورة والدفع ومنع الانتقال غير الصحيح.
- تثبيت الاسم والكود والوحدة والسعر والضريبة والعنوان.
- أولوية قواعد التسعير وتعارضها والحد الأدنى للكمية والصلاحية.
- الضرائب الشاملة وغير الشاملة والمتعددة والتقريب.
- حدود الخصم والتجاوز بسبب وصلاحية.
- حساب الهامش من الكلفة المثبتة لا من الكلفة الحالية.
- السقوف التراكمية للتسليم والفوترة والدفع والمرتجع.

### 14.2 اختبارات `SQL` (قاعدة البيانات)

- مستخدمان يؤكدان آخر وحدة: ينجح حجز واحد فقط.
- تأكيد طلب البيع لا يغيّر `OnHand` (الرصيد الفعلي)، ويغيّر `Reserved` (المحجوز) و`Available` (المتاح).
- تسليم جزئي يستهلك جزءاً من الحجز وينقص المخزون مرة واحدة وينشئ الحركة والتكلفة.
- إعادة محاولة ترحيل التسليم لا تكرر الأثر.
- فاتورة كمية مطلوبة/مسلمة لا تتجاوز أهلية المصدر.
- ترحيل الفاتورة ينشئ ذمة وإيراداً وضريبة متوازنة مرة واحدة.
- دفعتان متزامنتان لا تتجاوزان الرصيد المستحق.
- دفعة واحدة توزع على عدة فواتير وعدة دفعات تسوي فاتورة واحدة.
- المرتجع يعيد الكمية المقبولة فقط ويحافظ على اللوط/التسلسل.
- الإشعار الدائن والاسترداد لا يتجاوزان القيمة الأصلية.
- عزل شركتين لكل الجداول والعلاقات والفهارس الجديدة.
- مطابقة المخزون والحركات والقيود بعد المسار الكامل والعكس.

### 14.3 اختبارات الأمان والواجهة

- منع الرابط المباشر لكل فعل دون الصلاحية.
- منع `overposting` (إرسال حقول غير مسموحة) بتحديد نماذج الأوامر.
- رمز مكافحة التزوير لكل عملية تغيير.
- رحلة عربية وإنجليزية واتجاه `RTL` (من اليمين إلى اليسار).
- إخفاء العملية المنتهية وإظهار الحالة والرابط للمستند التالي.
- رسائل الأخطاء القابلة للحل تربط بالإعداد الصحيح حسب الصلاحية.
- كل نجاح يعرض الخطوة التالية وشرحاً قصيراً ورابطاً آمناً.

## 15. أثر الواجهة / Frontend impact

الواجهات الجديدة المطلوبة تدريجياً:

1. ملف زبون احترافي ببطاقات معلومات واتصالات وعناوين وائتمان.
2. قوائم أسعار وقواعد بواجهة متجاوبة دون تمرير أفقي.
3. قائمة عروض أسعار مع بحث وفلاتر وحالات وإجراءات متاحة فقط.
4. شاشة عرض سعر سريعة بالبحث باسم المنتج أو الباركود والوحدة.
5. تفاصيل طلب البيع مع شريط تقدم: طلب، حجز، تسليم، فاتورة، تحصيل، مرتجع.
6. شاشة الحجز تعرض المطلوب والمحجوز والمتاح والنقص.
7. شاشة تجهيز وتسليم جزئي مع اللوط/الرقم التسلسلي.
8. شاشة فاتورة زبون تعرض مصادر الكميات والأصل والمدفوع والمتبقي.
9. شاشة تحصيل وتخصيص واضحة على فاتورة أو عدة فواتير.
10. شاشة مرتجع وفحص وتصرف ثم إشعار دائن أو رد مبلغ.

لا يظهر زر للعملية بعد اكتمالها؛ يستبدل بحالة مثل "تم التأكيد" أو "مرحّل" ورابط للمستند الناتج.

### `SAL-020` — أساس التسعير والضريبة والوحدة / Pricing, tax and UOM foundation

### `SAL-030` — عروض الأسعار / Quotations

> **COMPLETED 2026-10-20.** القبول يغلق العرض كدليل تجاري؛ إنشاء طلب البيع مؤجل عمدًا إلى `SAL-040` حتى يبقى التحويل مستقل الصلاحية وقابلًا لمنع التكرار.

- مسودة، إرسال، قبول، رفض، انتهاء وإلغاء مع تاريخ دلالي.
- لقطات الزبون والعناوين والمنتج والوحدة والسعر والضريبة والعملة.
- قبول مرة واحدة يثبت قرار الزبون؛ `SAL-040` ينشئ طلب البيع مرة واحدة من العرض المقبول ويستبدل زر التحويل برابط المستند.
- قوالب العروض والمنتجات الاختيارية تؤجل إن لم تكن مطلوبة للإطلاق الأول.

**شرط الخروج:** عرض كامل من الواجهة إلى قاعدة البيانات دون أثر مخزني أو محاسبي.

### `SAL-040` — طلب البيع / Sales order

> **COMPLETED 2026-10-20.** التحويل من عرض مقبول وحيد على مستوى قاعدة البيانات، والتأكيد تجاري فقط بلا حجز أو حركة مخزون أو قيد.

- طلب مستقل وحالات تجارية وسجل تاريخ ونسخة تزامن.
- حالات التسليم والفوترة والدفع مشتقة ومستقلة.
- تأكيد الطلب لا ينقص الرصيد الفعلي.
- ربط البائع والفريق عند توفر أساس المؤسسة المطلوب.

**شرط الخروج:** طلب مؤكد قابل للتدقيق بلا حركة مخزون أو قيد.

### `SAL-050` — الحجز / Reservation

> **COMPLETED 2026-10-20.** فُعّل مصدر `SaleOrder` بحجوزات كاملة/جزئية متعددة مرتبطة ببند الطلب، مع تحرير وإعادة تخصيص وسياسة نقص صريحة وحماية تزامن، دون إنقاص الرصيد الفعلي أو إنشاء قيد.

- تفعيل مصدر `SaleOrder` (طلب بيع) الموجود في `InventoryReservation` (حجز المخزون).
- حجز كامل/جزئي، تحرير وإعادة تخصيص حسب المستودع والموقع.
- منع حجز آخر وحدة مرتين باختبار قاعدة بيانات متزامن.
- سياسة النقص: منع أو انتظار أو موافقة، ولا مخزون سالب ضمنياً.

**شرط الخروج:** `Available = OnHand - Reserved` (المتاح = الفعلي - المحجوز) تحت التزامن.

### `SAL-060` — التسليم / Delivery

> **COMPLETED 2026-10-20.** أضيف مستند تسليم مستقل جزئي/كامل يستهلك الحجز والموقع الدقيق، ينقص الرصيد الفعلي والمحجوز، يحفظ التتبع والكلفة والحركة الفعلية ويرحّل تكلفة البضاعة المباعة مرة واحدة، دون فاتورة أو تحصيل. الإلغاء بعد الترحيل محظور بانتظار مسار المرتجع المضبوط.

## 19. سبب كل تغيير معماري مهم / Rationale

| التغيير | السبب |
|---|---|
| فصل طلب البيع عن التسليم | التأكيد التزام تجاري وليس دليلاً على خروج البضاعة |
| فصل التسليم عن الفاتورة | يدعم التسليم والفوترة الجزئية وسياسات الكمية المطلوبة/المسلمة |
| فصل الفاتورة عن الدفع | يدعم الذمم والسداد الجزئي ودفعة لعدة فواتير |
| إبقاء الحجز في المخزون | المخزون وحده يملك التوفر والمواقع والتزامن |
| تثبيت الوصف والوحدة والسعر والضريبة | يحفظ الحقيقة التاريخية عند تغير البيانات الرئيسية |
| محرك تسعير مستقل | يمنع تكرار القواعد بين المبيعات و`POS` والتجارة الإلكترونية |
| حاسبة ضريبة مركزية | تمنع اختلاف الحساب بين العرض والفاتورة والمرتجع |
| مستند تسليم مستقل | يتيح عدة تسليمات وتجهيزاً وتتبعاً وعكساً مضبوطاً |
| بوابة ترحيل محاسبية واحدة | تمنع قيداً ناقصاً أو مكرراً وتطبق الفترة المالية |
| مفاتيح منع التكرار | تحمي المخزون والمال من النقر/إعادة المحاولة المكررة |
| مسار إضافي بجانب `Sale` | يحمي بيانات ووظائف البيع الفوري الحالية من الترحيل الخطر |
| تأجيل `BusinessPartner` (شريك الأعمال) | التوحيد مفيد مستقبلاً لكن كلفته ومخاطره لا تبرران البدء به قبل احتياجات الزبون الفعلية |

## 20. القرارات المعتمدة والخطوة التالية / Accepted decisions and next step

اعتمدت `SAL-005` القرارات التالية:

1. يبقى `POS` (نقطة البيع) مساراً فورياً مستقلاً في الإصدار الأول.
2. المنتجات المخزنية تفوتر على المسلّم، والخدمات قد تفوتر على المطلوب وفق سياسة سطر مثبتة.
3. يثبت `COGS` (تكلفة البضاعة المباعة) عند ترحيل التسليم.
4. تثبت المستندات الجديدة العملة وسعر الصرف المؤرخ من أول شريحة تجارية، ولا يفعل الأثر المالي قبل تجهيز الحسابات والاختبارات.
5. السياسة الافتراضية حجز كامل ومنع مخزون سالب، مع توسعة مستقبلية لحجز جزئي مضبوط.
6. تبدأ المرحلة العملية بـ`SAL-010` لتطوير ملف الزبون، ثم `SAL-020` للتسعير والضريبة والوحدة.

التفاصيل الملزمة موجودة في `SALES_ARCHITECTURE_ALIGNMENT.md`. الخطوة التالية هي تنفيذ `SAL-010` كشريحة كاملة بعد مراجعة كود الزبائن الحالي.
