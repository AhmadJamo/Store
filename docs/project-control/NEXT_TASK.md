## `P1-AUD-011` — مخطط حدث التدقيق والكاتب الأساسي

> الحالة: PROPOSED — AWAITING APPROVAL (مقترحة وتنتظر الموافقة)

> الاعتماد السابق: اكتمل تصميم `P1-AUD-010` دون تغيير تشغيلي. العقد والحدود وخطة الرجوع في
> [../AUDIT_SECURITY_ARCHITECTURE_AND_IMPLEMENTATION_PLAN.md](../AUDIT_SECURITY_ARCHITECTURE_AND_IMPLEMENTATION_PLAN.md)
> والقرار في [../decisions/2026-10-15-audit-event-v2-boundary.md](../decisions/2026-10-15-audit-event-v2-boundary.md).

### الهدف

إضافة أساس `AuditEvent` (حدث التدقيق) فقط: كيان وجدول إضافيان، عقد كاتب في Application (طبقة التطبيق)،
تنفيذ في Infrastructure (البنية التحتية)، منقح بقائمة سماح وبصمة HMAC-SHA256 (بصمة موثقة بمفتاح)، كلها
خلف feature flag (مفتاح تشغيل) مغلق افتراضيًا.

### داخل النطاق

- عقد الحقول والـenums (القيم الثابتة) المعتمدة في التصميم.
- قيد Scope/TenantId، الفهارس وحدود الأطوال والحمولة.
- كاتب للحدث الناجح داخل UnitOfWork (وحدة العمل) ومنقح يمنع الأسرار افتراضيًا.
- مفتاح سلامة خارجي بنسخة key version (إصدار المفتاح)، دون وضع السر في المستودع.
- اختبارات rollback، شركتين، Platform، التنقيح، منع التكرار والتحقق من البصمة.
- ترحيل إضافي وتطبيقه على Demo بعد نسخة/نقطة رجوع مناسبة ومصالحة المخطط.

### خارج النطاق

- لا شاشة عرض أو تصدير.
- لا تغطية جميع الخدمات؛ تبدأ التغطية الدلالية في `P1-AUD-012`.
- لا إيقاف أو تعديل أو backfill (تعبئة تاريخية) لسجل `AuditLogs` القديم.
- لا سياسة حذف/أرشفة فعلية ولا ادعاء مقاومة عبث كاملة قبل checkpoint (نقطة تثبيت) خارجي وصلاحيات SQL منفصلة.
- لا تخزين كلمات مرور أو `token` (رمز وصول) أو بيانات دفع حساسة.

### القبول

1. migration (ترحيل) إضافي لا يغير 707 سجلات `AuditLogs` الحالية.
2. حدث النجاح يرجع مع معاملة الأعمال، ولا يبقى بعد rollback.
3. نطاق الشركة والمنصة يفشل مغلقًا ولا يسمح بتسرب بين شركتين.
4. قائمة السماح وحدود الحجم تمنع الأسرار والحمولات الخام.
5. `OperationId` يمنع التكرار حيث يلزم، والبصمة تُنشأ وتُتحقق بمفتاح خارج القاعدة.
6. feature flag مغلق افتراضيًا وخطة الرجوع لا تحذف دليلًا.
7. البناء واختبارات الأمان وSQL (قاعدة البيانات) ذات الصلة ناجحة وموثقة.
