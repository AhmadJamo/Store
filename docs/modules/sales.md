# Sales
> Status: LEGACY IMMEDIATE SALE IMPLEMENTED; SAL-020 THROUGH SAL-130A IMPLEMENTED IN SOURCE | Last reviewed: 2026-10-24

`SAL-130A` exposes quote-to-cash analytics through the generic Analytics Center provider contract. It calculates quotation cohort/value/acceptance, order progression, posted invoice revenue, collection, outstanding/overdue receivables, credits, delivery COGS, contribution, customer/product performance and an explicitly separated legacy/modern comparison. The provider is read-only; it does not invent conversions between legacy immediate sales and the modern document lifecycle.

`SAL-120B` centralizes organization identity and reusable document design in Settings. The identity source contains bilingual trade/legal names, registration/contact/address details, a separately loaded logo and custom per-document fields. Versioned document designs add paper/language, RTL-ready logical margins, colors/font, header/logo/name placement, visibility controls, cover/header/footer/watermark text and ordered bilingual sections. An active quotation design can be selected by a quotation template or overridden on an individual quotation. Draft quotations have a live PDF preview; sending atomically freezes the effective identity, exact design/sections, customer/content/lines/totals and optional logo in a hash-protected snapshot. Every later PDF is rebuilt from that snapshot, so subsequent settings changes cannot alter history. The reusable PDF engine is feature-neutral and ready for invoices, orders, receipts and reports; no customer portal is active.

SAL-120A adds tenant-owned, versioned quotation templates. A Draft template defines validity, channel, optional price list, reusable introduction/terms/footer, required/optional/alternative products, quantity bounds, fixed or editable quantities, option groups and whether extra lines are allowed. Activation validates the complete configuration, archives an older active version with the same code and can set one active tenant default. Active templates are immutable; change occurs through a higher version.

Applying a template never trusts stored or browser-submitted prices. `SalesQuotationService` reloads the active template, validates every expected item and group, overrides product/unit/tax identifiers from the server-side template and calls the existing pricing evaluator for the selected customer and quotation date. The resulting quotation freezes the template code/version/name, reusable content and selected-line section/type/group evidence. Creating or applying a template does not reserve stock, create a delivery, post accounting or collect payment. The complete staged plan and competitor research are in `SAL120_ADVANCED_QUOTATION_TEMPLATES_PLAN.md`.

SAL-110 adds flexible tenant-configured controls at Sales Order confirmation. Each active rule can target every customer or one customer, compare order company amount, credit exposure, overdue days, discount percentage or margin percentage, and Warn, RequireApproval or Block. Approval rules merge into one ordered role workflow with configurable requester self-approval and distinct-approver safeguards. The review freezes measured evidence and decisions; the order remains Draft until final approval and no stock or accounting authority is invoked.

The implemented `Sale` flow is classified by the completed `SAL-000` audit as a compatible immediate sale/invoice/payment/stock workflow. It is not a Sales Order and must not be backfilled into invented quotations, deliveries, receivable invoices or payment allocations. The additive target, risks and sequence are documented in `SALES_ARCHITECTURE_AUDIT_AND_IMPLEMENTATION_PLAN.md`; `SAL-005` fixes the ownership boundaries. Customer foundation CUS-005..030B preserves every historical CustomerId and now provides profile/code/archive/concurrency, contacts/addresses, configurable receivable assignment, payment days, preferred configured currency and tax/exemption defaults. SAL-020B adds an optional prospective default price list. These commercial values do not silently change or rewrite the legacy immediate Sale.

Customer create/edit render nested `Form.*` fields and post an explicit `CustomerFormPostDto` wrapper with the same shape. Generated customer code is not an input prerequisite, and an empty receivable-account selection is accepted by model binding so shared/automatic account policy can resolve it; manual policy produces a localized, specific account-selection error. Other profile and commercial fields remain optional except the customer name and server-provided language/time-zone defaults. Invalid submissions rebuild the option lists, preserve attempted values, show an all-errors summary plus field errors and add a localized correction prompt instead of failing silently. Create/edit forms declare their target actions and submit buttons explicitly. Regression protects the post-model contract, optional generated/policy fields and visible validation/submit markup.

MOD-005 adds a coexisting Angular Customer vertical slice over the same `CustomerService`: permission-separated internal API list/details/form/create/update, server paging/search/sort, full bilingual responsive forms, Problem Details feedback and explicit row-version conflict handling. `MOD-024E` exposes Sales Delivery list/details, draft preparation from an active reservation, Post and draft Cancel through Angular.

Sales quantity, threshold, price-rule and document-line decimal ranges parse limits and submitted values with invariant culture. Arabic UI requests no longer throw before controller execution when validating dot-based HTML decimals.

Wholesale Create and Retail POS call `SalesController.Create` then `SaleService.CreateAsync`. Product choices are limited to active products enabled for the corresponding channel, and the service revalidates those flags against crafted requests. It validates discount rules, generates the tenant document number, chooses the server-side price, applies the optional invoice tax after discounts, decreases stock at the current warehouse average and writes the Sale movement in one UnitOfWork transaction. Sale freezes the selected tax percentage, inclusive policy, output account and amount; SaleItem freezes UnitCost and CostOfGoodsSold. The number, sale, valuation and movement commit or roll back together; ProductStock rowversion detects concurrent writes.

For a prepared-to-order item, SaleService requires an active recipe, snapshots its version and derives the sale-line unit cost from recipe quantities and current warehouse ingredient averages. It aggregates/consumes ingredients instead of decrementing menu-item stock. A missing or insufficient ingredient blocks the sale unless controlled negative consumption is enabled; such consumption uses provisional cost for later variance settlement.

Sales and POS require a payment method mapped to a settlement account. The Details screen can post the sale once: debit settlement, debit configured net invoice discount when present, credit branch/default net revenue, credit the frozen output-tax account, debit COGS and credit warehouse inventory. Inclusive tax is extracted without increasing settlement; exclusive tax is added. Source type/reference uniqueness blocks duplicate posting. Sources include `SalePostingService`, Sale/SaleItem, sales DTOs/controller/views and accounting repositories/settings.

Tracked direct products and tracked recipe ingredients are issued from non-expired balances inside the sale transaction using the warehouse's FIFO, FEFO, location-priority or minimize-locations policy. Manual policy uses deterministic FIFO until explicit audited identity override is delivered. The immutable tracking trace records the invoice reference; serial-tracked issues require whole units.

Wholesale and POS sale lines may optionally submit exact lot/serial allocations. The POS cart shows the compact selection only for directly stocked tracked products. The allocation must equal the line quantity and the immutable issue rows record `Manual`; leaving it empty uses and records the warehouse strategy. Prepared-product ingredient overrides are not exposed because the sold line is not the ingredient identity.

Posted sales support partial or full immutable returns. The service subtracts all earlier returned quantities, prevents over-return, allocates original invoice discount and tax proportionally, refunds through the original payment account and creates a source-unique posted reversal journal. Tracked direct goods require explicit lot quantities or unique serial identifiers issued by the original sale, and already-returned identities are rejected. Direct stocked goods return to the original warehouse at the frozen sale-line cost and reverse COGS; prepared-to-order goods do not recreate consumed ingredients or reverse their COGS.

POS terminals have a branch, default warehouse and prioritized warehouse allow-list. The POS screen filters warehouses after terminal selection. SaleService verifies the active terminal, branch warehouse permission and warehouse POS eligibility before changing stock, and the Sale records `PosTerminalId` for audit. Legacy POS remains available only while no terminals are configured.

Each configured terminal can also have its own POS experience profile. Retail, grocery, cafe, restaurant and quick-service presets initialize the product layout, card density, touch sizing, search focus, visible product data, theme, accent, header, cart side and grid columns. The POS applies the selected terminal's persisted settings at runtime. This phase changes presentation and operator ergonomics; restaurant tables, kitchen routing, modifiers, scales and specialty order workflows remain future operational features.

POS terminals also define enabled and default order types across Walk-in, Dine-in, Takeaway and Delivery. Restaurant/cafe profiles can capture a table or service reference, dine-in guest count and per-item preparation notes; grocery and quick-service profiles can retain fast barcode-entry behavior. SaleService validates the selected type and enabled fields against the terminal configuration and persists the order context on Sale/SaleItem. This is the durable order-context foundation; table occupancy, kitchen tickets/routing, delivery dispatch, modifiers and scale integration remain separate workflow features.

SAL-020A fixed price-rule precedence, managed-unit normalization, dated exchange-rate direction, final rounding, tax/exemption snapshots and an explainable result. SAL-040 converts an Accepted quotation once into a separately numbered Sales Order. The order copies rather than recalculates every commercial header and line snapshot, retains restrictive source links, and supports Draft, Confirmed and reasoned Cancelled states with semantic history and rowversion. Database uniqueness prevents a second order or duplicate source line. The quotation conversion button disappears and becomes a generated-order link. Confirmation itself creates no reservation, stock movement, journal, invoice or payment.

SAL-050 adds a separate reservation page for confirmed orders. Operators select a warehouse by name and an optional active reservable location, enter only remaining stock-unit quantities, and choose either all-or-nothing or reserve-available shortage handling. Each reservation preserves its source order line and allocation dimensions. Multiple records allow release and reallocation without rewriting history; order cancellation releases all active reservations. Completed line/full-order actions disappear in favor of localized completion state and reservation-history links. Serializable transactions, balance rowversions and SQL integration prevent two orders from claiming the final unit. OnHand, stock movements and journals remain unchanged.

SAL-060 adds independent `SalesDelivery` documents in Draft, Posted and Cancelled states. A Draft selects one active reservation/warehouse and may deliver all or part of each remaining reservation line. Posting atomically removes the exact reserved warehouse/location stock, records lot/serial allocation when applicable, decreases both OnHand and Reserved, freezes moving-average unit cost and COGS, writes Sale stock transaction plus SalesDeliveryOut physical movement, and posts debit COGS / credit warehouse Inventory through the shared journal gateway. Partial consumption leaves only the undelivered remainder reserved; final consumption closes the reservation. A posted delivery cannot be cancelled or repeated, and the sales order cannot be cancelled after any posted delivery; a controlled return workflow owns later reversal.

SAL-070 adds independent `CustomerInvoice` documents and controlled ordered/delivered eligibility. SAL-080 adds receivable/revenue/tax posting and exact reversal. SAL-090 adds independent `CustomerPayment` receipts that allocate partially or fully across posted invoices for the same customer/currency. Posted allocations derive Unpaid/Partially Paid/Paid; the receipt journal debits the payment-method asset, credits frozen receivable carrying values and records explicit realized exchange differences. Reversal preserves history, exactly reverses accounting and reopens balances. Completed actions disappear, invoice/payment/journal links remain available, and no collection operation changes inventory. Legacy Sale/POS remains unchanged.

SAL-100A adds independent `CustomerReturnRequest` authorization from one Posted delivery. Approval records history only: stock, accounting, invoice balances, credit notes and refunds remain unchanged until the later receipt/inspection and credit-note slices. SAL-100B adds partial/multiple `CustomerReturnReceipt` documents for Approved requests. Each line freezes received quantity, exact tracked identities, inspection notes and Restock/Quarantine/Reject/Destroy disposition. SAL-100D adds a separate Posted `CustomerCreditNote` for returned quantities billed by a Posted invoice.
