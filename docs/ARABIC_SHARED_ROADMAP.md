# خطة العمل المشتركة لنظام MiniStore ERP / SaaS

> هذا الملف هو مرجع العمل اليومي المشترك بين صاحب المشروع وCodex.
> آخر تحديث: 2026-09-15
> مصدر الحقيقة الفني: الكود والترحيلات الفعلية. عند اختلاف هذا الملف مع الكود، نراجع الكود ثم نحدّث الملف.

## 1. الهدف

بناء نظام ERP سحابي متعدد الشركات يصلح للبيع كخدمة SaaS، ويحافظ على ثلاثة حدود واضحة:

1. **إدارة المنصة:** لصاحب البرنامج وموظفيه، وتشمل الشركات والخطط والاشتراكات والدفعات والدعم.
2. **إدارة الشركة:** لصاحب المنشأة وموظفيه، وتشمل المحاسبة والمخزون والمبيعات والمشتريات والفروع والصلاحيات.
3. **التشغيل اليومي:** واجهات سريعة حسب الدور، مثل POS وأمين المستودع والمحاسب ومدير الفرع.

نجاح النظام لا يقاس بعدد الصفحات، بل بصحة الأرصدة، وعزل الشركات، وإمكانية تتبع كل حركة، ومنع تعديل المستندات المالية بعد اعتمادها دون عملية عكس واضحة.

## 2. طريقة استخدام هذا الملف

### حالات المهام

- `[ ] مخطط`: لم يبدأ التنفيذ.
- `[-] قيد التنفيذ`: المهمة الحالية التي نعمل عليها.

### قاعدة العمل بيننا

1. نعمل على مهمة رئيسية واحدة في كل مرة حتى لا تتداخل قواعد المحاسبة والمخزون والصلاحيات.
2. قبل البدء نثبت نطاق المهمة، وقواعد العمل، وشروط القبول.
3. أثناء التنفيذ نعدل جميع الطبقات المتأثرة: Domain ثم Application ثم Infrastructure ثم Web.
4. بعد التنفيذ نشغل البناء والفحوص المناسبة ونطبق الترحيل عند وجود تغيير في قاعدة البيانات.
5. تحت المهمة المكتملة نكتب تاريخ الإنهاء، ما تم فعلياً، دليل التحقق، وأي قيود بقيت.
6. بعد كل مهمة مكتملة نضيف **خمسة اقتراحات جديدة** إلى قسم الاقتراحات، ناتجة عن العمل الذي انتهى.
7. الاقتراح لا يصبح مهمة ملزمة إلا بعد نقله إلى قائمة التنفيذ وترتيبه حسب الأولوية.

### تعريف الإنجاز Definition of Done

لا نضع `[x]` على أي مهمة إلا عند تحقق البنود المناسبة لها:

- قواعد العمل مكتوبة ومطبقة في الخادم، وليس في JavaScript فقط.
- عزل الشركة `TenantId` موجود على كل بيانات تشغيل جديدة مع الفلاتر والحماية.
- لا يصل Controller مباشرة إلى EF عند إضافة مسار جديد؛ يمر عبر Application.
- كل عملية مالية أو مخزنية ذرية وتنجح أو تتراجع بالكامل.
- الصلاحيات مفروضة في الخادم ومخفية في الواجهة أيضاً.
- الواجهة الجديدة عربية وإنجليزية وتدعم RTL/LTR.
- توجد معالجة للتزامن عند تعديل رصيد أو حالة أو إعداد حساس.
- الترحيل موجود ومطبق، ولا توجد تغييرات EF غير مرحّلة.
- البناء ناجح دون أخطاء، والفحوص ذات العلاقة ناجحة.
- التوثيق و`AI_WORKLOG` و`TODO` محدثة.

### أهم الفجوات الآن

1. تعريفات الأدوار وصلاحيات الأدوار غير الإدارية ما زالت مشتركة بين الشركات.
2. لا يوجد متوسط تكلفة مرجح متحرك فعلي ولا قيد تكلفة بضاعة مباعة.
3. المبيعات لا تنشئ قيداً محاسبياً كاملاً يشمل الضريبة والخصم والتحصيل وCOGS.
4. لا توجد مرتجعات أو قيود عكس أو فترات مالية مغلقة.
5. بوابة الدفع الحقيقية وWebhooks غير مربوطة بعد.

## 4. ترتيب التنفيذ المنطقي

### المرحلة صفر: تثبيت العمليات الحرجة

#### ERP-001 — إعداد ترقيم المستندات بصورة مضمونة

- [x] **الحالة:** مكتمل.
- **الأولوية:** حرجة.
- **السبب:** إنشاء تحويل مخزني يتوقف حالياً إذا لم يوجد سجل `DocumentNumberSettings`.
- **منطق العمل المنفذ:**
  - لكل شركة سجل واحد لكل نوع مستند: مبيعات جملة، POS، تحويل مخزني، وقيد يومية.
  - ينشأ السجل الافتراضي عند أول عرض للإعدادات أو أول توليد دون أن يتوقف العمل بسبب غيابه.
  - يدعم Prefix وSuffix وقالباً مرناً وطول الرقم والرقم التالي وبداية وفترة إعادة العداد.
  - القوالب تدعم السنة والشهر واليوم، وتمنع إعادة العداد إذا لم يحمل الرقم تاريخاً كافياً، كما تمنع إرجاع التسلسل إلى فترة أقدم.
  - الرقم التالي يمكن رفعه فقط، و`RowVersion` يمنع ضياع تعديل إداري متزامن.
- **Workflow المنفذ:** إعداد الشركة ← قراءة تسلسل نوع المستند ← تطبيق إعادة الفترة عند الحاجة ← توليد الرقم وزيادة العداد داخل Transaction المستند ← حفظ الاثنين أو التراجع عنهما معاً.
- **تاريخ الإنهاء:** 2026-09-15.
- **ما تم:** شاشة إعدادات عربية/إنجليزية موحدة مع معاينة فورية، واستبدال إعدادات البيع والتحويل القديمة، وربط مبيعات الجملة وPOS والتحويلات وقيود شراء اليومية بالخدمة المركزية.
- **القرارات:** رقم فاتورة المورد يبقى مرجعاً خارجياً كما أدخله المستخدم، بينما رقم قيد اليومية رقم داخلي مستقل. تغيير الإعدادات يؤثر في المستندات الجديدة فقط.
- **الترحيل:** `20260915070028_UnifyDocumentNumbering` مطبق على قاعدة MiniStore المحلية؛ نقل العدادات القديمة وأنشأ النواقص لكل شركة قبل حذف الجدولين السابقين.
- **التحقق:** بناء Release ناجح دون تحذيرات، 178 فحصاً ناجحاً، لا تغييرات EF غير مرحّلة، وتطبيق قاعدة البيانات ناجح.
- **القيود المتبقية:** اختبار تصادم فعلي بطلبين متوازيين على SQL ضمن ERP-002؛ لا توجد بعد تسلسلات داخلية لفواتير الشراء أو المرتجعات لأنها تحتاج مستنداتها وقواعدها أولاً.
- **الاقتراحات الخمسة الجديدة:**
  1. السماح بتجاوز التسلسل حسب الفرع أو نقطة البيع مع رجوع تلقائي لتسلسل الشركة.
  2. إضافة سنة مالية ورمز فرع ورمز POS كرموز قالب بعد تثبيت الفترات المالية.
  3. تقرير فجوات الأرقام والأرقام الملغاة مع سبب الإلغاء والمستخدم.
  4. سجل تدقيق خاص بكل تغيير في قالب أو عداد الترقيم قبل التشغيل القانوني.
  5. إنشاء رقم داخلي مستقل لفاتورة الشراء إلى جانب رقم فاتورة المورد.

### المرحلة الأولى: إكمال عزل المستخدمين والصلاحيات

#### SEC-001 — أدوار وصلاحيات مملوكة لكل شركة

- [x] **الحالة:** مكتمل.
- **الأولوية:** عالية جداً قبل زيادة عدد الشركات الحقيقية.
- **منطق العمل:**
  - يكون الدور تابعاً لشركة، وله اسم ظاهر ووصف وصلاحيات داخلها فقط.
  - تستطيع شركتان إنشاء دور باسم “مدير فرع” بصلاحيات مختلفة.
  - يبقى دور مالك الشركة محمياً ولا يمكن لمستخدم منح نفسه صلاحيات إدارة المستخدمين.
  - يمنع تعيين دور لشخص لا يملك عضوية نشطة في الشركة.
  - إلغاء العضوية يبطل الجلسات والتعيينات الفعالة.
- **Workflow:** إنشاء الدور ← اختيار الصلاحيات ← تعيينه للمستخدم ← تقييمه مقابل الشركة الموجودة في الجلسة.
- **شروط القبول:** نفس المستخدم يستطيع امتلاك دور مختلف في شركتين دون تسرب اسم الدور أو صلاحياته.
- **تاريخ الإنهاء:** 2026-09-15.
- **ما تم:** إنشاء `TenantRole` و`TenantRolePermission` وربط تعيين المستخدم بالدور المحلي، وتحويل صفحات الأدوار والمستخدمين إلى واجهات عربية/إنجليزية تعرض بيانات الشركة الحالية فقط.
- **القرارات:** تبقى Identity مسؤولة عن الحساب وكلمة المرور، بينما اسم الدور وصلاحياته وتعيينه أصبحت داخل حدود الشركة. دور Admin محمي ولا يعدل أو يحذف، وصلاحيات إدارة المستخدمين والأدوار لا تفوض لدور عادي.
- **الترحيل:** `20260915074008_AddTenantOwnedRoleDefinitions` نسخ الأدوار والصلاحيات والتعيينات القديمة لكل شركة قبل حذف الربط العام، و`20260915083946_EnforceTenantRoleAssignmentBoundary` فرض تطابق الشركة والدور بمفتاح أجنبي مركب؛ كلاهما مطبق.
- **التحقق:** بناء Release ناجح بلا تحذيرات، و187 فحصاً ناجحاً، ولا تغييرات EF غير مرحّلة. فحص قاعدة البيانات وجد صفراً من التعيينات اليتيمة وصفراً من الشركات بلا Admin محمي، واختبار HTTP أعاد 200 للدخول و302 صحيحاً من Roles للزائر.
- **القيود المتبقية:** واجهة تغيير أدوار مستخدم موجود ودعوات المستخدمين وتبديل الشركة ضمن SEC-002/SEC-003، وسجل تدقيق قيم الصلاحيات التفصيلي مهمة لاحقة.
- **الاقتراحات الخمسة الجديدة:**
  1. نسخ دور موجود أو تطبيق قالب جاهز للمحاسب وأمين المستودع والكاشير ومدير الفرع.
  2. شاشة تعرض الصلاحيات الفعلية للمستخدم ومصدر كل صلاحية لتسهيل التشخيص.
  3. نطاقات بيانات للدور حسب الفرع والمستودع وPOS بعد تثبيت نموذج التفويض.
  4. تفويض محدود لإنشاء الأدوار بسقف صلاحيات لا يتجاوز صلاحيات المفوّض.
  5. سجل تدقيق قبل/بعد لتعديلات الدور والصلاحيات وتعيينات المستخدمين.

#### SEC-004 — تقوية عزل علاقات الشركات داخل قاعدة البيانات

- [x] **الحالة:** مكتمل.
- **تاريخ الإنهاء:** 2026-09-15.
- **ما تم:** إنشاء سجل مركزي ثابت يصنف كل Entity، وتحويل كل علاقة بين سجلين يحملان `TenantId` إلى مفتاح أجنبي مركب يفرض تطابق الشركة داخل SQL Server. شمل ذلك المنتجات والمستودعات والمواقع والمخزون والمشتريات والمبيعات والتحويلات والفروع وPOS والحسابات والعملاء والموردين والضرائب ووسائل الدفع والاشتراكات واستخدامات الخصم.
- **القرارات:** تبقى فلاتر EF وحماية SaveChanges خط الدفاع الأول، وتصبح المفاتيح المركبة خط دفاع مستقل داخل قاعدة البيانات. يفشل فحص الانحدار إذا أضيف Entity بلا تصنيف أو بقيت علاقة Tenant غير مركبة.
- **الترحيل:** `20260915121458_HardenTenantIsolationRelationships` و`20260915121859_HardenTenantSubscriptionRedemption` مطبقان محلياً.
- **التحقق:** 59 علاقة Tenant مركبة، وصفر علاقات Tenant غير محمية. رفض SQL محاولة نقل رصيد مخزون من الشركة 1 إلى الشركة 2 بخطأ FK 547، وبقي السجل الأصلي دون تغيير بعد Rollback. بناء Release ناجح و191 فحصاً ناجحاً ولا تغييرات EF غير مرحّلة.
- **القيود المتبقية:** SQL Row-Level Security وحسابات اتصال منفصلة محدودة الصلاحيات تحتاج تصميم بيئة الاستضافة والإدارة قبل الإنتاج؛ اختبارات الاختراق الخارجية ما زالت عملاً تشغيلياً لاحقاً.
- **الاقتراحات الخمسة الجديدة:**
  1. تقرير صحة للعزل يعرض أي Entity غير مصنفة أو FK غير مركب ضمن CI.
  2. حزمة Integration Tests تنشئ شركتين وتختبر كل Repository ضد تمرير IDs من الشركة الأخرى.
  3. حساب SQL محدود للتطبيق وحساب منفصل للترحيلات والإدارة.
  4. منع `IgnoreQueryFilters` وSQL الخام في مسارات ERP إلا باستثناء موثق ومراجع.
  5. تقييم SQL Row-Level Security بعد تثبيت أسلوب الاستضافة والاتصال والإدارة.

### المرحلة الثانية: محرك تكلفة المخزون

#### ACC-001 — المتوسط المرجح المتحرك Moving Weighted Average

- [ ] **الحالة:** مخطط.
- **الأولوية:** أساسية قبل قيد المبيعات وCOGS.
- **البيانات المطلوبة:** تكلفة متوسطة حالية لكل `Product + Warehouse`، قيمة مخزون، ولقطة تكلفة على كل حركة مؤثرة.
- **قاعدة الشراء الأساسية:**

  `المتوسط الجديد = ((الكمية القديمة × المتوسط القديم) + تكلفة صافي الكمية المستلمة) ÷ الكمية الجديدة`

- **صافي تكلفة الشراء:** سعر السطر بعد خصم السطر، مع معالجة خصم الفاتورة والضريبة حسب كون الضريبة قابلة للاسترداد أو جزءاً من التكلفة.
- **قواعد إضافية:**
  - البيع لا يعيد حساب المتوسط؛ يستخدم المتوسط الموجود لحظة الترحيل.
  - النقل بين مستودعين ينقل الكمية بتكلفتها من المصدر ويؤثر في متوسط الوجهة حسب السياسة المعتمدة.
  - الموقع الدقيق داخل المستودع لا يملك متوسطاً مستقلاً ما دام التقييم على مستوى المستودع.
  - الرصيد الصفري يحتفظ بآخر متوسط مرجعي أو يصفر وفق قرار موثق، ولا يسمح بقسمة على صفر.
  - يمنع المخزون السالب افتراضياً لأنه يشوه التكلفة، ويمكن لاحقاً جعله خياراً مضبوطاً للمنشأة.
- **Workflow:** استلام شراء ← حساب صافي التكلفة ← قفل سجل الرصيد ← تحديث الكمية والمتوسط والقيمة ← تسجيل حركة تكلفة ← إنشاء/ربط القيد.
- **شروط القبول:** مثال يدوي معروف يعطي نفس المتوسط والقيمة في النظام، والتزامن لا ينتج متوسطين مختلفين.

#### ACC-002 — سجل تقييم مخزون قابل للتدقيق

- [ ] **الحالة:** مخطط.
- كل حركة تحفظ: الكمية قبل/بعد، المتوسط قبل/بعد، قيمة الحركة، نوع المصدر، رقم المستند، المستخدم والوقت.
- لا يعدل السجل بعد إنشائه؛ التصحيح يكون بحركة عكس.

- **قيد الإيراد والتحصيل:**
  - مدين: صندوق/بنك وسيلة الدفع، أو حساب العميل عند البيع الآجل.
  - مدين: حساب خصم المبيعات عند اعتماد عرض الخصم منفصلاً.
  - دائن: حساب إيراد الفرع، وإلا حساب الإيراد الافتراضي.
  - دائن: ضريبة المخرجات.
- **قيد التكلفة:** مدين تكلفة البضاعة المباعة، دائن مخزون المستودع، بالقيمة الناتجة عن المتوسط لحظة البيع.
- **Workflow:** Draft sale ← Validate ← Post once ← تخفيض المخزون ← تثبيت تكلفة السطور ← إنشاء قيد متوازن مرتبط بالفاتورة.
- **شروط القبول:** لا يمكن ترحيل الفاتورة مرتين، ومجموع المدين يساوي الدائن، ويظهر الفرع والمستودع والعميل ووسيلة الدفع على الأبعاد المناسبة.

#### ACC-004 — اكتمال دورة المشتريات

- [ ] **الحالة:** مخطط.
- توحيد لحظة استلام المخزون مع لحظة الترحيل المحاسبي أو فصل Receipt عن Invoice بصورة صريحة.
- تثبيت توزيع خصم الفاتورة على السطور لأغراض تقييم المخزون.
- منع تعديل فاتورة شراء مرحلة، والسماح فقط بالإلغاء عن طريق مستند عكس.

#### ACC-005 — المرتجعات والقيود العكسية

- [ ] **الحالة:** مخطط.
- مرتجع بيع يرجع الكمية بالتكلفة المثبتة على سطر البيع الأصلي، لا بمتوسط اليوم.
- مرتجع شراء يخرج الكمية حسب سياسة تكلفة موثقة ويعكس الضريبة والخصم والدائن.
- كل عكس يرتبط بالمستند الأصلي ويحفظ السبب والمستخدم ووقت الموافقة.

#### ACC-006 — الفترات المالية والإقفال

- [ ] **الحالة:** مخطط.
- فترة Open تسمح بالترحيل، SoftClosed تتطلب صلاحية خاصة، Closed تمنع أي مستند مالي جديد.
- إعادة الفتح تتطلب صلاحية عالية وسبباً وسجل تدقيق.
- تواريخ المستندات تستخدم المنطقة الزمنية للشركة، بينما يخزن وقت النظام بصيغة UTC.

### المرحلة الرابعة: الاشتراكات والفوترة الفعلية

#### SaaS-001 — نسخ الخطط وحفظ شروط الاشتراك

- [ ] **الحالة:** مخطط.
- تعديل خطة لا يغير عقد الشركات القديمة بصمت.
- يحتفظ الاشتراك بنسخة السعر والعملة والحدود والميزات التي وافقت عليها الشركة.
- الترقية تطبق فوراً أو في الفترة التالية حسب السياسة، والتخفيض غالباً في التجديد.

#### SaaS-002 — فرض جميع حدود الخطة

- [ ] **الحالة:** مخطط.
- الحدود الحالية للمستخدمين والمستودعات توسع لتشمل الفروع وPOS والمنتجات والتخزين والميزات.
- التحقق يكون في Application قبل الحفظ، وتعرض الواجهة الاستخدام الحالي والحد بوضوح.
- تخفيض الخطة لا يحذف بيانات؛ يمنع إنشاء المزيد ويطلب معالجة التجاوز.

#### SaaS-003 — ربط مزود دفع حقيقي

- [ ] **الحالة:** متوقف على اختيار الدولة ومزود الدفع والعملة القانونية.
- **Workflow:** إنشاء Checkout داخلي ← إنشاء جلسة عند المزود ← رجوع المستخدم ← Webhook موقع من المزود ← Idempotency check ← تفعيل الاشتراك ← إيصال/سجل تدقيق.
- صفحة الرجوع لا تعتبر دليلاً على الدفع؛ الـWebhook الموثق هو المصدر النهائي.
- نحتاج سياسات فشل الدفع، Grace Period، إعادة المحاولة، الإلغاء، الاسترداد والنزاع.

#### SaaS-004 — إدارة مشغلي المنصة وتأمينهم

- [ ] **الحالة:** مخطط.
- شاشة لإضافة وتعطيل Owner/Administrator/Billing/Support.
- تفعيل 2FA إلزامي للمنصة، جلسات قصيرة، سجل دخول، وتنبيه عند محاولات غير معتادة.
- كل تعديل على شركة أو اشتراك أو دفعة أو Promo Code يدخل في PlatformAuditLog.

### المرحلة الخامسة: التشغيل المتقدم للمخزون وPOS

#### INV-001 — اقتراحات التزويد بين المخزن الخلفي ومنطقة العرض

- [ ] **الحالة:** مخطط.
- Min/Max لكل منتج وموقع أو POS، مخزون متاح، كمية بالطريق، أولوية المستودعات، وطلب تزويد قابل للمراجعة قبل التنفيذ.

#### INV-002 — Picking وPutaway ذكيان

- [ ] **الحالة:** مخطط.
- دعم FIFO/FEFO عند وجود تواريخ تشغيلات وصلاحية، وترتيب المسار حسب المنطقة والممر والرف.
- المنتجات بلا موقع تبقى في قائمة عمل واضحة ولا تختفي من رصيد المستودع.

#### POS-001 — سير عمل المطاعم والكافيهات

- [ ] **الحالة:** مخطط.
- الطاولات وحالتها، الإضافات Modifiers، الوجبات المركبة، طابعة/شاشة المطبخ، فصل ودمج الفاتورة، وتوجيه الأصناف حسب محطة التحضير.

## 6. قائمة الاقتراحات الجديدة

هذه القائمة تبقى دائماً وفيها خمسة اقتراحات على الأقل. بعد إنهاء كل مهمة نضيف خمس نقاط جديدة مرتبطة بنتيجتها:

1. لوحة صحة النظام تعرض آخر ترحيل، أخطاء الوظائف، فشل القيود، وفروقات المخزون.
2. معالج إعداد أولي للشركة يتأكد من الحسابات والفروع والمستودعات والضرائب ووسائل الدفع قبل التشغيل.
3. مركز موافقات موحد للتحويلات والخصومات والتسويات وإعادة فتح الفترات.
4. صندوق إشعارات داخل النظام للمهام التي تحتاج إجراء، مثل Unassigned Stock وقرب انتهاء الاشتراك ونقص المخزون.
5. تقارير تدقيق تربط المستند التجاري بحركة المخزون وقيد اليومية والمستخدم ضمن مسار واحد.
6. تجاوز تسلسل المستند حسب الفرع أو POS مع تسلسل الشركة كإعداد افتراضي.
7. رموز قالب للسنة المالية والفرع والجهاز بعد تنفيذ الفترات المالية.
8. تقرير فجوات وأرقام مستندات ملغاة يوضح السبب والمستخدم.
9. سجل غير قابل للتعديل لتغييرات إعدادات الترقيم والعدادات.
10. رقم شراء داخلي مستقل عن رقم فاتورة المورد الخارجي.
11. نسخ الأدوار وقوالب جاهزة للوظائف الشائعة.
12. عارض الصلاحيات الفعلية للمستخدم ومصدرها.
13. نطاق بيانات الدور حسب الفرع والمستودع ونقطة البيع.
14. تفويض إدارة الأدوار ضمن سقف صلاحيات آمن.
15. تدقيق قبل/بعد لتغييرات الأدوار والصلاحيات والتعيينات.
16. تقرير صحة آلي لتصنيف Entities وعلاقات Tenant ضمن CI.
17. اختبارات شركتين على كل Repository ومسار مستند تجاري.
18. منع تجاوز Query Filters أو SQL الخام دون استثناء معماري موثق.
19. حساب SQL محدود للتطبيق وحساب مستقل للترحيلات والإدارة.
20. تقييم Row-Level Security بعد تثبيت بنية الاستضافة والإدارة.
