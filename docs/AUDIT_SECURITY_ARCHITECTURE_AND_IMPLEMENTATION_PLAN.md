# Audit security architecture and implementation plan

> الحالة: APPROVED DESIGN — `P1-AUD-011..014` IMPLEMENTED
> المهمة: `P1-AUD-010..014`
> التاريخ: 2026-10-16
> مصدر الحقيقة الحالي: الكود، مخطط قاعدة Demo، وسجلات المجال الفعلية

## 1. النتيجة التنفيذية

سجل `AuditLog` الحالي مفيد كأثر عام بسيط، لكنه لا يكفي للتحقيق الأمني أو التشغيلي: لا يحفظ نتيجة العملية،
سببها، معرّف الترابط، القيم المنقحة قبل/بعد، قناة التنفيذ أو دليل مقاومة العبث. كما أنه يكتب من
`SaveChanges` (حفظ تغييرات قاعدة البيانات)، ولذلك لا يرى العمليات المرفوضة أو الفاشلة، وقد يلتقط معرّفًا
غير نهائيًا عند إضافة كيان يولّد رقمه داخل قاعدة البيانات.

نُفّذ أساس `AuditEvent` (حدث تدقيق) بعقد صريح وكتابة عبر طبقة Application (التطبيق)،
مع إبقاء `AuditLogs` القديمة كما هي خلال انتقال محدود. لا يصبح حدث التدقيق بديلًا عن القيد المحاسبي أو حركة
المخزون أو تاريخ حالة المستند؛ بل يشير إلى المصدر المختص ويضيف سياق من نفّذ العملية ونتيجتها وترابطها.

نفّذ `P1-AUD-011` الكيان والجدول والكاتب والمنقح والبصمة ومفتاح التشغيل، وطُبق الترحيل على Demo في
2026-10-16. فعّل `P1-AUD-012` المفتاح محليًا لبيئة Demo عبر User Secrets (مخزن الأسرار)، وربط الأدوار/الصلاحيات وست مجموعات إعدادات حساسة بالحفظ الذري. أضاف `P1-AUD-013` فشل/قفل الدخول والرفض الفعلي وإدارة المنصة ووصول تكامل الموردين، مع كاتب مستقل ظاهر الفشل ودليل طلب مقنّع. أضاف `P1-AUD-014` قارئًا منفصلًا للشركة والمنصة وصلاحيات مستقلة للعرض والتصدير والدليل الحساس، وتقسيم صفحات وتصديرًا محدودًا ومسجلًا. لا يضيف التفعيل وحده حدثًا مصطنعًا؛ تمتلئ `AuditEvents` فقط عند تنفيذ عملية مشمولة. بقيت سجلات `AuditLogs` القديمة دون إعادة تفسير أو تعبئة.

## 2. الجرد الحالي

### 2.1 السجل العام

| الجزء | الموجود الآن | الفجوة |
|---|---|---|
| `AuditLog` | رقم، اسم كيان، معرّف كيان، Added/Modified/Deleted، مستخدم، وقت، و`TenantId` (معرّف الشركة) مخفي في EF | لا نتيجة/سبب/ترابط/قناة/قبل وبعد/تصنيف حساسية/نسخة عقد/تكامل |
| `AuditSaveChangesInterceptor` | يضيف سطرًا لكل كيان متتبع مضاف أو معدل أو محذوف داخل حفظ الشركة | يتجاوز الحدث إذا لم توجد شركة، لا يسجل الرفض والفشل، ويعامل تغييرًا تقنيًا كحدث أعمال |
| القراءة | `AuditEventReadService` ومستودع معزول وشاشتا شركة ومنصة مع تصدير CSV محدود ومسجل | الاحتفاظ والأرشفة ونقطة التثبيت الخارجية لاحقة |
| مخطط Demo | 707 أسطر موزعة على أربع شركات، منها 32 بهوية `System`؛ لا معرّفات `Unknown` في الفحص السابق | لا يثبت اكتمال التغطية أو صحة الدلالة، ولا توجد سياسة احتفاظ |

### 2.2 مصادر حقيقة متخصصة يجب عدم نسخها

| المصدر | سلطته |
|---|---|
| `JournalEntry` و`JournalEntryLine` | المبالغ المدينة والدائنة، المصدر، تاريخ الترحيل والعكس المحاسبي |
| `StockMovement`, `StockTransaction`, `LocationMovement` | الحركة المادية، الكلفة، الرصيد قبل/بعد والموقع |
| `InventoryTrackingTransaction` | اللوط/الرقم التسلسلي واستراتيجية السحب والتتبع |
| `PurchaseRequestHistory`, `PurchaseOrderLifecycleHistory`, `StockTransferHistory` | انتقالات الحالة والسبب التشغيلي المعتمد للمستند |
| سجلات المطابقة والعكس والأسعار والاتصال بالمورد | الدليل التفصيلي المختص للعملية |
| `SupplierExternalAuditEvent` | قناة المورد الخارجية والفاعل والنتيجة والترابط والعنوان؛ نموذج قابل لإعادة الاستخدام لا مصدر عام بديل |
| حقول Created/Approved/Posted/Cancelled | هوية ووقت حالة المستند نفسها |

قاعدة الملكية: `AuditEvent` يجيب **من، متى، من أين، ما النتيجة، لماذا، وما المرجع**. المصدر المختص يجيب
**كمية/مبلغ/حساب/حالة المستند الصحيحة**. واجهة التحقيق تصل بينهما باستخدام المرجع ومعرّف الترابط ولا تنسخ
التفاصيل المالية أو المخزنية.

## 3. نموذج التهديد

| التهديد | التحكم المطلوب |
|---|---|
| تعديل أو حذف أثر بعد تنفيذ عملية مميزة | تخزين append-only (إضافة فقط)، منع update/delete عن هوية التطبيق، بصمة محتوى وتثبيت دوري خارج قاعدة التشغيل |
| إخفاء عملية بسبب rollback (رجوع المعاملة) | حدث النجاح داخل معاملة العمل؛ حدث الرفض/الفشل الأمني في مسار مستقل ولا يدعي أن تغيير الأعمال تم |
| تسرب أسرار أو بيانات شخصية في before/after | قائمة سماح للحقول، منقح مركزي، حدود حجم، اختبارات أسرار إلزامية |
| قراءة سجل شركة أخرى | نطاق صريح Platform/Tenant، فلتر شركة، مستودع تطبيق، صلاحيات واختبارات شركتين |
| إساءة مسؤول التصدير أو الوصول | صلاحية منفصلة، سبب مطلوب، وتسجيل قراءة/تصدير السجل نفسه |
| تكرار الحدث تحت إعادة المحاولة | `OperationId`/مفتاح idempotency (منع التكرار) فريد ضمن النطاق ونوع الحدث عند الحاجة |
| ترتيب مضلل تحت التزامن | رقم متزايد للعرض مع `OccurredAtUtc`؛ لا يُفهم الرقم كترتيب أعمال عالمي |
| تزوير هوية الفاعل | هوية تقنية ثابتة + نوع فاعل؛ الاسم المعروض لقطة اختيارية منقحة وليس سلطة |
| حذف صفوف كاملة دون كشف | checkpoint (نقطة تثبيت) دورية موقعة/محمية خارج قاعدة التشغيل، مع فحص فجوات وعدّ وبصمات |
| تضخم السجل أو payload (حمولة) خبيثة | أحجام قصوى، JSON (بيانات منظمة) مضبوط، فهارس محددة وسياسة احتفاظ وأرشفة |

## 4. ما يُسجل وما لا يُسجل

### يسجل إلزاميًا

- إنشاء/تعديل/تعطيل/أرشفة البيانات الرئيسية الحساسة والإعدادات.
- تغييرات المستخدمين والأدوار والصلاحيات والعضوية والشركة والخطة والاشتراك.
- الموافقة والرفض والتجاوز والترحيل والعكس والإلغاء وإعادة الفتح والإغلاق.
- فشل تسجيل الدخول، القفل، استخدام break-glass (وصول طارئ)، والعمليات المميزة المرفوضة.
- إنشاء أو إلغاء مفاتيح التكامل، بوابة المورد، الاستيراد والتصدير والوصول إلى سجل التدقيق.
- تغيير سياسات الاحتفاظ والتنقيح والتكوين الأمني عند توفرها.

### لا يسجل كنسخة تفاصيل

- بنود القيد المحاسبي أو رصيد الحساب؛ يحفظ مرجع القيد فقط.
- كميات وحسابات حركة المخزون؛ يحفظ مرجع الحركة أو المستند فقط.
- كامل المستند أو المرفق أو نص البريد أو جسم طلب HTTP.
- كلمات المرور أو بصماتها، cookie (ملف جلسة)، token (رمز وصول)، مفاتيح API، أسرار callback، رؤوس Authorization، بيانات دفع كاملة أو محتوى ملف.
- عمليات القراءة العادية منخفضة الحساسية؛ الاستثناء هو القراءة المميزة والتصدير والاطلاع على التدقيق.

## 5. عقد `AuditEvent` المقترح

العقد لغة-neutral (محايد اللغة)؛ الأكواد المخزنة لا تُترجم، وتُترجم تسمياتها فقط عند العرض.

| الحقل | القاعدة |
|---|---|
| `Id` | `bigint` متزايد للترقيم الفني فقط |
| `EventId` | `Guid` فريد ثابت عبر النقل والأرشفة |
| `SchemaVersion` | يبدأ بـ1 ويحدد طريقة تفسير الحمولة |
| `Scope` | `Tenant`, `Platform`, أو `System` |
| `TenantId` | مطلوب فقط عند `Tenant`، وفارغ في Platform/System مع check constraint (قيد تحقق) |
| `OccurredAtUtc` | وقت UTC من ساعة الخادم |
| `EventType` | كود ثابت مثل `Security.RolePermissionsChanged` |
| `Category`, `Severity`, `Outcome` | تصنيف ثابت؛ النتيجة `Succeeded`, `Denied`, `Failed` أو `Unknown` |
| `Action` | فعل محايد مثل Create/Approve/Post/Reverse/Export |
| `ActorType`, `ActorId` | User/System/External/Support؛ المعرّف nullable (اختياري) للحالات المجهولة |
| `SourceChannel` | Web/Worker/Api/Portal/Import/Platform |
| `CorrelationId` | معرّف الطلب أو سير العملية؛ مطلوب |
| `CausationId` | الحدث/العملية التي سببت هذا الحدث عند توفرها |
| `OperationId` | مفتاح ثابت لإعادة المحاولة؛ فريد انتقائيًا عند العمليات الحساسة |
| `ResourceType`, `ResourceId` | مرجع الكيان أو المستند دون نسخ محتواه |
| `ReasonCode`, `ReasonRedacted` | كود مطلوب للتجاوز/الرفض/العكس، ونص محدود ومنقح عند الحاجة |
| `ChangesRedactedJson` | أزواج حقول مسموحة قبل/بعد؛ لا تخزين تلقائي لكل خصائص الكيان |
| `MetadataRedactedJson` | مراجع إضافية مسموحة فقط، بحجم أقصى ونسخة عقد |
| `RequestPathTemplate` | قالب المسار لا URL كاملًا ولا query string (معاملات الرابط) |
| `SourceIpMasked`, `UserAgentHash` | عنوان مقنّع وبصمة لا القيمة الخام، وباحتفاظ أقصر |
| `IntegrityKeyVersion`, `IntegrityHash` | HMAC-SHA256 (بصمة موثقة بمفتاح) على تمثيل canonical ثابت للحدث |
| `RecordedAtUtc` | وقت قبول السجل وقد يختلف قليلًا عن وقت وقوع الحدث |

الفهارس المقترحة: `(TenantId, OccurredAtUtc DESC, Id DESC)`, `(CorrelationId)`,
`(ResourceType, ResourceId, OccurredAtUtc DESC)` وفلتر فريد لـ`OperationId` حيث يكون مطلوبًا. لا يوضع JSON
كله في فهرس، والاستعلامات دائمًا pagination (تقسيم صفحات) وحد تاريخ.

## 6. مسارا الكتابة

1. **حدث تغيير ناجح:** تنشئ خدمة Application الحدث الدلالي داخل `UnitOfWork` (وحدة العمل) نفسها. إذا رجعت
   المعاملة فلا يبقى حدث نجاح. تستمر آلية `AuditLog` القديمة مؤقتًا كأثر توافق ولا تُعد المصدر الجديد.
2. **رفض أو فشل أمني:** يسجل بعد انتهاء معاملة الأعمال عبر كاتب أمني مستقل محدود. يحمل `Denied/Failed`
   ولا يحتوي before/after مزعومًا، وفشل كتابته يطلق إنذارًا ولا يُخفى. لا يُستخدم هذا المسار للتحايل على
   ذرية العمليات المالية.

لا تُنشأ الأحداث من Controller (المتحكم) مباشرة، ولا يصل المتحكم إلى EF. تملك Application عقد الكاتب، وتنفذه
Infrastructure (البنية التحتية). `AuditSaveChangesInterceptor` يبقى fallback (احتياطًا) مؤقتًا، ثم يُجمّد بعد
وصول التغطية والمصالحة إلى الصفر؛ لا يُحذف تاريخ `AuditLogs`.

## 7. التنقيح والخصوصية

- الافتراضي deny (منع): لا يدخل أي حقل قبل/بعد إلا بتسجيله في قائمة سماح لكل `EventType`.
- تُمنع أسماء وأنماط: password, hash, token, secret, authorization, cookie, card, CVV، محتوى المرفق والجسم الخام.
- البريد والهاتف والعنوان والاسم تُقنّع إلا عندما يكون التغيير نفسه موضوع تحقيق مصرح به.
- المبالغ والكميات لا تُنسخ من دفترها؛ يسمح بدلًا منها بمعرّف المستند ونوع القرار والفارق المصنف عند الضرورة.
- يفشل الاختبار والبناء عند محاولة تمرير حقل محظور، وتطبق حدود طول على كل نص وحمولة JSON.

## 8. الوصول والاحتفاظ

الصلاحيات المقترحة: `AuditEvents.View`, `AuditEvents.Export`, `AuditEvents.ViewSensitive` و
`AuditRetention.Manage`. لا توجد صلاحية تعديل أو حذف يدوي. مستخدم الشركة يرى شركته فقط. مشغل المنصة يرى
أحداث المنصة؛ الوصول الاستثنائي إلى شركة يتطلب break-glass وسببًا وحدث تدقيق مستقلًا. كل تصدير يسجل غرضه
ونطاقه وعدد السجلات وبصمة الملف، ولا يسجل محتوى الملف نفسه.

افتراضات الاحتفاظ المقترحة التي تحتاج اعتمادًا قانونيًا/تشغيليًا قبل التنفيذ:

| الفئة | المدة الافتراضية المقترحة |
|---|---:|
| صلاحيات/إدارة/ترحيل/عكس/تجاوز مالي | 7 سنوات |
| تغييرات تشغيلية وبيانات رئيسية | 3 سنوات |
| عنوان IP المقنّع وبصمة المتصفح وفشل المصادقة التفصيلي | 90 يومًا، ثم تجميع غير معرف حتى سنة |
| سجلات المجال والقيود والحركات | تتبع سياسة مصدرها المختص، لا سياسة AuditEvent |

`LegalHold` (حجز قانوني) يوقف الإتلاف. الإتلاف وظيفة خلفية موثقة بعد أرشفة ومصالحة، وليس زرًا في الواجهة.
لا تطبق هذه المدد على بيانات فعلية قبل موافقة مالك النظام/الاستضافة والمتطلبات القانونية للبلد.

## 9. مقاومة العبث وحدودها

- مرحلة أولى: صفوف غير قابلة للتعديل من المجال، بصمة HMAC بمفتاح خارج قاعدة البيانات، واختبارات تمنع update/delete.
- عند توفر هويات SQL منفصلة: هوية الكاتب INSERT فقط وهوية القارئ SELECT فقط؛ الترحيلات بحساب نشر منفصل.
- مرحلة تشغيلية: checkpoint يومي يشمل المدى والعدد وجذر بصمات، ويُثبت في مخزن خارج قاعدة التشغيل مع تنبيه
  عند الفجوة أو اختلاف البصمة.
- النسخة الاحتياطية المشفرة والاستعادة الدورية تبقى لازمة لكنها لا تجعل السجل tamper-proof (عصيًا على العبث).

البصمة داخل القاعدة تكشف العبث ببيانات الصف عند عدم امتلاك مفتاحها؛ ولا تكشف حذف كل الأثر بثقة إلا بعد وجود
نقطة تثبيت خارجية. لذلك لا يدعي النظام "عدم قابلية العبث" قبل اكتمال المرحلتين.

## 10. الترحيل والتوافق والرجوع

1. إضافة جدول `AuditEvents` وقيوده وفهارسه فقط؛ لا تعديل أو backfill (تعبئة تاريخية) لـ`AuditLogs`.
2. نشر الكاتب خلف feature flag (مفتاح تشغيل) مغلق، ثم تشغيله لشركة Demo.
3. dual-write (كتابة مزدوجة) محدودة: السجل القديم يستمر، والأحداث الدلالية الجديدة تكتب للمسارات المعتمدة.
4. تقرير مصالحة يقارن العمليات المتوقعة بالأحداث الجديدة دون مقارنة سطر بسطر مع السجل القديم المختلف دلاليًا.
5. بعد تغطية معتمدة، إيقاف interceptor القديم للكتابات الجديدة مع إبقاء الجدول read-only تاريخيًا.
6. إزالة التوافق لا تتم إلا بقرار مستقل وبعد نافذة رجوع.

الرجوع قبل cutover (التحويل): إغلاق feature flag ووقف الكاتب الجديد؛ لا حذف أحداث كتبت. الرجوع بعد التحويل:
إعادة تشغيل السجل القديم مؤقتًا وforward-fix (إصلاح أمامي)، لا إسقاط الجدول ولا حذف الدليل. أي ترحيل غير قابل
للعكس يحتاج نقطة backup (نسخة احتياطية) مثبتة وموافقة.

## 11. الاختبارات الإلزامية قبل التفعيل

- حدث واحد لكل عملية ناجحة مع حماية إعادة المحاولة، ولا حدث نجاح بعد rollback.
- حدث Denied/Failed مستقل لا يدعي تغييرًا منجزًا.
- شركتان + نطاق Platform دون تسرب، والغياب في السياق يفشل مغلقًا.
- قائمة السماح تخفي كل الأسرار والبيانات الشخصية المحددة.
- فشل متعمد في كاتب التدقيق الحرج يمنع commit أو ينتج تنبيهًا موثقًا حسب تصنيف الحدث.
- تزامن وترتيب pagination، وحدود حجم، وفهارس بخطة استعلام مقبولة.
- منع update/delete بهوية التطبيق واكتشاف تغيير البصمة/الفجوة/checkpoint.
- صلاحيات العرض والتصدير والوصول الحساس، وتسجيل التصدير نفسه.
- مصالحة Demo بعد migration، وبناء واختبارات الانحدار وSQL (قاعدة البيانات).
